# Production deployment and privacy operations

M27 supplies application foundations and deployment configuration, not a deployed Azure environment. `.env.production.example` contains placeholders only. `compose.yaml` remains the existing **local development** topology (backend host 3001, PostgreSQL host 55432, MinIO 59000/59001). Its local credentials, HTTP cookie exception and host.docker.internal model address are not a production deployment recipe.

## Deployment sequence

1. Build and scan the existing `backend/Dockerfile` targets `runtime`, `worker`, and `migrations`. Push immutable versioned images to Azure Container Registry. Grant the deployment identity only the required image-pull permissions. Build `frontend/` with Node 22.23.2, replace the API-origin/public-ID meta tags for the target deployment, and publish `frontend/dist/frontend/browser` on an HTTPS static host (Azure Static Web Apps, Storage static hosting behind an HTTPS ingress, or equivalent). No credentials belong in frontend build variables.
2. Provision private PostgreSQL Flexible Server, PostgreSQL 17, with `vector` and `pgcrypto` allowlisted/enabled. Preserve the existing 1,024-dimensional schema, FTS and pgvector/RRF retrieval. Validate extension versions and query plans in staging. Azure requires allowlisting before extension activation; the SQL extension name is `vector`. [Azure pgvector documentation](https://learn.microsoft.com/en-us/azure/postgresql/extensions/how-to-use-pgvector).
3. Provision a private S3-compatible object store reachable by backend and worker. This adapter speaks the S3 protocol; **Azure Blob Storage is not a drop-in replacement**. Use a supported private S3 service/MinIO deployment or explicitly budget a later Blob adapter. Block anonymous bucket access; scope credentials to the application bucket, use TLS, encryption at rest, versioning and monitored backups. Keep the console and storage administration endpoints private.
4. Store database/storage credentials, the independent rate-limit HMAC secret and metrics token in Azure Key Vault. Use Container Apps secret references and a managed identity with least-privilege vault access, then bind secrets as environment variables. Never place values in source, image layers, CLI arguments, resolved Compose output or deployment logs. [Container Apps Key Vault references](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets).
5. Run one controlled migration job with the `migrations` image and a migration-only DB role, before rolling out backend/worker. Do not run concurrent app-start migrations. Capture a verified backup first, inspect the migration, run `npm run migrate -- up`, and verify `SELECT count(*) FROM pgmigrations` and the subscription backfill. Restrict the application DB role from DDL/trigger modification. The application requires tenant tables plus audit INSERT; audit UPDATE/DELETE must remain prohibited. Keep database credentials distinct from migration credentials.
6. Deploy the backend `runtime` image to Container Apps or equivalent with HTTPS ingress; route to `PORT` (production example: 3001). Configure GET `/api/health` as liveness and GET `/api/ready` as readiness, with startup delay and thresholds suitable for DB startup. Readiness checks PostgreSQL connectivity; it does not currently prove model/storage availability. Add separate synthetic model/storage checks and alerts. Keep a minimum replica available if cold-start latency is unacceptable.
7. Deploy the `worker` image separately with no public ingress, at least one continuously running replica, adequate OCR RAM/CPU, private DB/storage/AI connectivity, and a graceful termination budget longer than normal jobs. It polls both durable ingestion and object cleanup. Scale only within database pool and AI inference capacity. Monitor queued/stale ingestion, cleanup oldest age/attempts, failures and storage growth; there is no separate worker HTTP listener. Object cleanup retry is indefinite, so alert rather than treating an empty terminal-failure list as health.
8. Configure DNS for API/admin frontend names and managed HTTPS certificates at ingress. Set `ADMIN_APP_ORIGIN` to one plain exact HTTPS origin (no path, command text, query, fragment or wildcard); strict `normalizeOrigin` validation remains. Keep the admin app and API on the same HTTPS site when using SameSite=Lax cookies. Cross-site admin hosting requires a deliberate future cookie/CORS design, not an exception to CSRF. Customer widget origins remain exact separately configured origins.
9. Keep `SESSION_COOKIE_SECURE=true`, `LOCAL_HTTP_DEVELOPMENT=false`, missing public Origin disabled, and secrets independent. Configure `TRUST_PROXY_HOPS` only after proving every request traverses exactly that many trusted hops and direct backend access is blocked; the proxy must replace attacker-supplied forwarding headers. Leave 0 when that cannot be guaranteed. Protect `/internal/metrics` with both its bearer secret and ingress/private-network restrictions. Keep high-cardinality customer usage in PostgreSQL.
10. Validate auth/CSRF, exact origins, ID rotation/disable, API keys, quotas, health, PDF/DOCX/OCR ingestion, RAG citations and restore rehearsals in staging before traffic cutover. Use rolling deployment compatible with the additive schema; rollback application images first. The M27 down migration destroys commercial history/keys and refuses to run with pending cleanup work. It is not a routine production rollback.

## AI hosting decision still required

Development retains local Ollama. Production must provision private, adequately sized Ollama-compatible inference compute for `qwen3.5:9b` and `qwen3-embedding:0.6b`, including availability, capacity, TLS/private routing, monitoring and model-image supply-chain controls. The current adapter has no cloud-provider credentials or provider-specific integration. Do not expose an unauthenticated Ollama listener publicly. The production example uses a private DNS placeholder, never host.docker.internal. Changing embedding models/dimensions requires a separate migration/reindex design; M27 preserves 1,024 dimensions.

## Configuration and operational limits

The production example lists all existing environment groups: database/pools, AI, RAG, storage, ingestion/OCR, auth/cookies/origin, rate limits, proxy, metrics and logging. Plan limits and display prices live in PostgreSQL `plans`, not environment variables. No payment-provider secret is required. The beta plan is active with a rolling 30-day period by default. Operators can edit plan configuration or an organization's subscription through a privileged DB change process; there is intentionally no plan-changing HTTP route.

For an approved operator change, select the intended organization and subscription under a transaction/row lock, update only `plan_code`/status or explicitly approved boundaries, set `updated_at`, and append an allowlisted `subscription.updated` audit event identifying the target organization. Keep period boundaries unchanged on a mid-period plan change to retain usage. Every referenced plan must exist. Downgrades preserve data; further growth is blocked until below quota. Do not update customer plans as a way to make acceptance tests pass; test fixtures use isolated schemas or explicitly created temporary organizations.

Resource/quota writes serialize per organization. Upload finalization holds a DB transaction and intent lock across a bounded storage PUT to prevent cleanup races; size and request limits remain active. Budget DB pools for uploads and set infrastructure timeouts above `OBJECT_STORAGE_TIMEOUT_MS` plus commit time. Production should consider a more elaborate upload state machine if this becomes a throughput bottleneck. Message quotas are shared across backend replicas; the legacy internal-chat short-window limiter is per process, public/key limits are shared PostgreSQL windows. Add edge rate limiting for volumetric attacks.

## Backups and recovery

Use PostgreSQL PITR/backups with a documented RPO/RTO, encrypted offsite storage and scheduled restore verification. Back up private objects, including manifests/checksums, separately. Include `plans`, subscriptions, counters, hashed keys and cleanup intents in DB backup inventories. Test restoring to isolated DB/buckets; never restore over the active customer database as a verification step. Existing `backup:postgres`, `backup:verify`, `backup:objects`, and `restore:objects` scripts remain applicable. Their local defaults are not Azure backup configuration.

For consistent snapshot-style backups: put writes in maintenance mode, drain active uploads and ingestion, stop workers gracefully, capture DB plus objects, then resume. Ensure queued cleanup records and objects are restored together. A DB restored to a newer snapshot than its object snapshot can otherwise reference missing private files. Apply retention and access restrictions to backups, including password/session/key hashes. Retain documented handling of deletion in backups and do not silently reintroduce deleted accounts during recovery.

## Organization deletion runbook (automation deliberately deferred)

There is no instant hard-delete account endpoint. An authorized operator must:

1. Verify the owner's request, organization identity, retention obligations and any holds through the approved support process. Record only safe request metadata.
2. Suspend the subscription, disable all public chatbots, revoke keys, stop new writes at ingress for that organization, and wait for in-flight chat/upload/worker work to finish. Subscription suspension alone does not disable export/revocation/deletion or every legacy metadata operation; maintenance controls are required.
3. Offer the owner the paginated metadata export and a separately authorized private-file export if required. JSON never contains document files or transcripts.
4. Invoke tenant-scoped document deletion for every document. Resolve any `STORAGE_RECONCILIATION_REQUIRED` legacy key before proceeding. Monitor `object_cleanup_jobs` until empty for this organization, reconcile its private bucket prefix including non-current object versions, and verify chunks/embeddings/jobs are gone. Do not cascade-delete document metadata as a shortcut around durable object cleanup.
5. In a reviewed DB transaction, remove the organization and its remaining commercial/membership metadata after a final inventory. Shared users must not be deleted if they belong to another organization; handle orphan user/session records under a separate authorized policy. API-key creator FKs must be considered before user removal.
6. Audit identifiers are historical immutable snapshots. Apply the documented security/legal retention policy to audit records through a privileged retention process; do not disable the append-only trigger ad hoc. Schedule backup/versioned-object expiration, record completion, and ensure restores reapply deletion records.

Automated full-account deletion, retention scheduling, private-file export packaging, and account recovery UX remain future privacy enhancements. Conversation persistence does not exist; no conversation deletion is invented here.

## M28 website and FAQ knowledge

Deploy the same HTTP and worker images with migration `1791400000000_website-knowledge.js` applied first. Keep one dedicated document loop and one dedicated crawl loop per worker replica. Each crawl issues requests sequentially and embeds sequentially; document embedding concurrency remains separately controlled by `INGESTION_EMBEDDING_CONCURRENCY`. Start with one worker, reserve database connections for both loops and cleanup, and size memory for a bounded 20 MB crawl plus prepared 1,024-dimensional vectors. Horizontal workers use PostgreSQL claims and fencing. Increasing replicas increases aggregate internet/inference traffic; use infrastructure replica caps. No new ports or Redis are needed.

Workers need public DNS and outbound HTTP/HTTPS to customer origins, and existing private connectivity to PostgreSQL, object storage and inference. The crawler rejects private/special-use addresses, validates every DNS answer, and pins the socket lookup to a validated address while keeping the original Host/SNI and certificate validation. Redirects repeat validation and cannot leave the exact origin. HTTP proxy environment variables are not used by this transport. Never disable TLS verification or substitute a trust-all agent.

Use defense-in-depth egress controls: deny crawler internet-path access to link-local/cloud metadata (`169.254.169.254`), private address ranges and internal management endpoints. Azure NSGs/firewalls/service-specific controls must be reviewed for platform virtual/metadata addresses, including Azure's platform networking addresses; application validation alone is not an egress boundary. Where possible route public website access through an egress firewall which cannot reach internal services. Preserve explicitly required private DB/storage/inference connections separately; do not accidentally block the worker's accepted ingestion dependencies. Do not enable authenticated/intranet crawling to work around blocked destinations.

All `CRAWLER_*` settings and validated defaults are in `.env.production.example`. No arbitrary cron input is accepted: schedules are manual, daily, weekly. The worker scheduler polls durable due times, deduplicates live jobs, and advances next-sync after completion/failure. The first sync is queued on creation. A 15-second heartbeat supports 60-second stale recovery; failed/recovered claims cannot finalize after their fencing token changes. Shutdown drains both loops. Allow at least the configured crawl duration plus one embedding timeout for graceful termination.

Monitor the protected `/internal/metrics` endpoint for `north_orbital_crawl_jobs{state}`, `north_orbital_crawl_queue_age_seconds` and `north_orbital_crawl_pages_processed`. These are database-backed gauges over retained jobs, not lifetime counters. Alert on oldest due work over 15 minutes, persistent running jobs with old heartbeats, growing failed-job counts, and repeated quota exhaustion. Customer/source identifiers never become labels. Inspect tenant-scoped administration/audit data for diagnosis; do not log URLs with query strings, page bodies, cookies or provider error text. Health/readiness remain independent of external websites.

Storage planning must include FTS/pgvector indexes and metadata. Plans have separate website-source, website/FAQ page, and indexed-content-byte quotas. Indexed-byte accounting includes UTF-8 chunk text plus 4,096 bytes per vector (not exact PostgreSQL index/storage overhead). PostgreSQL must have extra free capacity for atomic replacement and vacuum. Failed replacement/over-quota finalization rolls back; previous ready knowledge survives. Removed page metadata and terminal crawl jobs are pruned in bounded batches after 30 days; audit history follows the existing retention policy.

Website knowledge is customer-selected public data, but URLs, titles and text may still contain personal information. Public chat citations expose only bounded evidence and safe source metadata; the authenticated privacy export includes website metadata/schedules and FAQ content. Deletion cascades page/chunk/vector/job rows immediately. Backups and previously returned chat answers are not erased by deletion. Follow backup retention/export controls. Restore all source, page, chunk, job, subscription and usage tables together; run stale recovery before resuming workers and verify citations/tenant isolation after restore. Avoid restoring an old running worker alongside a restored database. Suspend automatic scheduling during an incident or mass restore until outbound load and source ownership have been reviewed.

Supported HTML is server-rendered; JavaScript is never executed. Responses must honor identity encoding (compressed responses are rejected), sitemap XML is strict and rejects DTD/entities, robots failures are conservative, and sources never broaden to another origin. Full M35 prompt-injection defense, authenticated sources and platform plugins remain deferred.
