# Milestone 25 + 26: public widget and platform security

This milestone adds the public boundary around the existing PostgreSQL RAG pipeline, authenticated administration, and recovery tooling. It does not change the accepted document/vector data model or introduce billing.

## Architecture and data

Customer website → Shadow DOM widget → public ID lookup → exact Origin check → shared PostgreSQL rate limit → existing tenant-scoped hybrid retrieval/query rewrite → bounded evidence → model → validated citations.

Administrator → Argon2id login → database-backed cookie session → CSRF check → current organization membership/role → existing tenant-scoped services.

Migration: `backend/migrations/1791200000000_public-platform-security.js`, after the accepted production-RAG migration. Adds public/branding columns, `chatbot_allowed_origins`, `users`, `organization_memberships`, `auth_sessions`, `rate_limit_windows`, `audit_events`, indexes and an audit immutability trigger. It does not delete/recreate organizations, documents, chunks or vectors. Existing and new chatbots default to **public disabled**. This security migration is deliberately forward-only; recovery uses verified backups.

Public IDs are `pub_` plus 24 cryptographically random bytes encoded as 48 hex characters (192 bits), generated by PostgreSQL/Node crypto, with a database UNIQUE constraint. They are distinct from internal UUIDs, public rather than secret, and never chosen by clients. Rotation replaces the ID immediately without rewriting documents/settings/origins. There is no public-ID cache. Slow chat requests recheck enabled state/ID after generation.

## Public API and origins

| Method | Route | Result |
|---|---|---|
| GET | `/api/public/chatbots/:publicId/config` | Only public ID and five branding fields |
| POST | `/api/public/chatbots/:publicId/chat` | `{message,history}` → answer, validated sources, fallback |
| GET | `/api/public/chatbots/:publicId/document-sources/:sourceId` | Ready-only, tenant-scoped metadata and excerpt of at most 1,500 characters |
| GET | `/widget/v1.js` | Versioned, customer-independent JavaScript bundle |

Public responses never include organization/chatbot UUID routing, storage keys, models, provider configuration, or allowed-origin lists. Source URLs use the public namespace. Citation buttons fetch the excerpt; opening the endpoint as a top-level navigation may lack Origin and is intentionally rejected.

Origins are parsed HTTP(S) origins, stored normalized and matched **exactly**. No paths, queries, fragments, credentials, wildcards, arbitrary subdomains, `null`, or unsafe schemes. Default ports/case normalize; an optional root slash in admin input normalizes away. Public browser headers must be serialized origins. Limit: 50 distinct origins per chatbot. Public responses vary on Origin, approved responses echo the exact origin, and no public credentialed CORS is enabled. OPTIONS validates the public ID and origin too. Missing Origin is rejected by default, including production. The optional missing-origin exception requires non-production plus explicit local development.

**Origin checking is not authentication:** HTTP clients can forge Origin. Public IDs are not secrets. Rate limits and deployment edge protections remain necessary. An enabled bot makes ready citation chunks accessible to clients that know its public ID and present an approved origin; do not enable a chatbot containing documents unsuitable for public access.

## Widget and Angular demo

```html
<script defer src="https://CHAT_HOST/widget/v1.js"
        data-chatbot="pub_REPLACE_WITH_THE_PUBLIC_ID"></script>
```

`widget/` is TypeScript, with no runtime dependencies, built using esbuild. Shadow DOM isolates CSS. It uses textContent, not HTML injection, for branding, model answers and document excerpts. Branding color is validated before assignment to a CSS variable. Citation endpoint URLs are constructed from validated IDs rather than model URLs. The launcher/panel support keyboard controls, focus restoration, Escape, accessible names and a live conversation region; narrow screens use viewport bounds. History is in memory only, capped at six messages/1,000 characters each; the rendered conversation is bounded too. No localStorage, analytics, tracking or third-party runtime script.

The Docker widget stage builds `v1.js`; the backend image serves it with JavaScript content type, `nosniff`, cross-origin resource permission and a one-hour cache. Configuration responses are no-store. No customer's public ID is compiled into the bundle. Non-Docker backend development: build `widget/`, then copy `widget/dist/v1.js` to `backend/widget/v1.js` (generated, ignored).

`docs/examples/widget.html` is a small embed page with a placeholder. Serve it from an approved origin; file URLs are not supported. Use a distinct API origin so browser GET requests carry Origin.

The existing Angular UI uses `north-orbital-chatbot` and `north-orbital-api-origin` meta tags in `frontend/src/index.html`. The checked-in demo meta tag contains the accepted local chatbot’s nonsecret public ID; replace it for another deployment or after rotation. The local API origin is `http://localhost:3001`. It requires no internal tenant UUID. Source buttons fetch bounded excerpts and display Angular-escaped text. Public branding controls the standalone widget; the demo retains its existing visual design.

## Branding and administrator API

Authenticated routes below are rooted at `/api/organizations/:organizationId/chatbots/:chatbotId`:

| Method | Suffix | Body/purpose |
|---|---|---|
| GET | `/public-settings` | Current ID, enabled state and branding (administrator/internal use) |
| PUT | `/branding` | Full validated branding object |
| PUT | `/public-access` | `{ "enabled": true }` or false |
| POST | `/public-id/rotate` | Server-generated replacement; no ID supplied |
| GET | `/allowed-origins` | Current exact origins |
| PUT | `/allowed-origins` | `{ "origins": ["https://example.com"] }`; validated/deduplicated transactional replacement |

Branding fields: `displayName` 1–80 characters; `welcomeMessage` 1–500; `accentColor` exactly `#RRGGBB`; `launcherLabel` 1–40; `launcherPosition` is `bottom-right` or `bottom-left`. Text is plain text, including any literal angle brackets. No logo URL, custom HTML, JavaScript or arbitrary CSS.

Disabling public access makes config, chat and sources return 404. Authenticated internal chat remains available. Public settings/origin changes and their audit insert commit atomically under a chatbot row lock.

## Authentication, sessions and roles

No public registration. Normalize email with trim/lowercase and enforce a unique `lower(email)` database index. Passwords require 12–256 characters, with no composition rules, and use salted Argon2id (64 MiB, three iterations, parallelism one). Unknown and incorrect accounts use the same error and an Argon2 verification path. No password/hash is returned.

- `POST /api/auth/login`: email/password; exact `ADMIN_APP_ORIGIN` header required, including CLI use. Rate limited. Returns safe user data and a CSRF token; sets the session cookie.
- `GET /api/auth/me`: safe user ID/email only, no state mutation.
- `POST /api/auth/logout`: authenticated and CSRF-protected; deletes the server session and expires the cookie.

Tokens are 32 random bytes (256 bits). Only SHA-256 hashes of session and CSRF tokens are stored. The raw session token exists only in the HttpOnly cookie; the CSRF token is returned at login and must be kept in admin-client memory and sent in `X-CSRF-Token`. Unsafe methods require it, including uploads, chat/testing, rotation and logout. GET/HEAD/OPTIONS do not mutate session state. Login again if the admin client loses its CSRF token. Cookies have Path=/api, SameSite=Lax, no Domain, a bounded TTL (default seven days) and Secure by default. Plain HTTP cookies require explicit local loopback development configuration. Expired/deleted sessions fail every new request immediately. Cleanup runs bounded batches every minute in the backend, and sessions are still checked for expiry before cleanup.

| Role | Policy |
|---|---|
| owner | All organization operations, including public settings/security changes |
| admin | Chatbot/document administration, branding, public access/rotation, origins and audit viewing |
| member | Reads and CSRF-protected internal chat; no uploads/retry/security mutations or audit viewing |

Every organization route checks current membership before invoking its handler. Nonmembers get privacy-preserving 404. Cross-chatbot/document/source IDs remain checked by scoped services/repositories. Organization creation requires a session/CSRF and inserts organization, creator owner membership and audit records in one transaction. No membership-management HTTP endpoints are added; controlled owner bootstrap is the only membership-writing tool, and cannot demote/remove owners. Invitation and membership-management UX are deferred.

Protected legacy namespaces include organizations, chatbots, document list/get/upload/retry, internal tenant chat, tenant sources and legacy fixture source endpoints. There is no unguarded internal-ID chat/upload fallback. Liveness/readiness remain public; operational metrics have separate authentication.

### Local bootstrap

```sh
cd backend
npm run security:init
npm run migrate -- up
# zsh: silent prompt; never put the password in argv or a committed file
read -s 'OWNER_PASSWORD?Owner password: '
printf '%s' "$OWNER_PASSWORD" | npm run auth:create-owner -- \
  --email owner@example.com --organization ORGANIZATION_UUID
unset OWNER_PASSWORD
```

The CLI reads a bounded password from piped stdin, hashes it and transactionally creates/reuses the user and grants owner membership to an existing organization. Reusing an existing account requires the matching password; it never silently resets a password. CLI failures omit input/hash/database details. The private `.env.security.local` generated at repository root is created exclusively with mode 0600; existing files are preserved. Compose reads it for backend and worker. Production must supply its own secret configuration instead of this local HTTP file.

## Rate limits, proxy and HTTP security

PostgreSQL fixed windows use atomic upserts, so limits work across backend instances. Keys are HMAC-SHA256 over a server-selected policy/scope/client tuple; no raw IP/account is stored in limit rows. Shared instances must share the same secret. Defaults:

- Public chat: 30/minute per public ID + client IP.
- Login: 5/15 minutes independently per client and account (protects against both account spraying and distributed attempts on one account).
- Upload and manual retry: combined 20/hour per user + organization.

429 includes Retry-After. Failed public chat validation counts; uploads/retries count before multipart parsing. Windows reset without sleeps; expiry cleanup runs with session cleanup. A PostgreSQL outage fails closed rather than bypassing a limit. Fixed-window boundary bursts are a beta limitation; use an edge limiter for volumetric abuse and operational ceilings.

`TRUST_PROXY_HOPS=0` ignores forwarded addresses by default. Set an exact trusted hop count only when **all** traffic is forced through that many Azure/nginx/load-balancer hops and direct backend access is blocked. The ingress must replace untrusted forwarded headers. Varying path lengths make a hop-count policy unsafe; redesign the network or implement explicit proxy-address trust before deployment.

Admin CORS uses the single exact `ADMIN_APP_ORIGIN` with credentials. Customer origins never authorize admin cookies. Helmet supplies CSP, frame protections, nosniff/referrer policy and HSTS; terminate production TLS correctly. Widget JS overrides resource policy to permit customer-page loading. Expose only intended API/UI ports through the ingress; PostgreSQL/MinIO/console ports in Compose remain loopback bound.

## Upload/storage protection

The accepted 20 MiB default, signature/extension validation, PDF/DOCX handling, private MinIO objects, tenant keys, durable jobs, retries, OCR deadlines, text/chunk bounds and ready-only retrieval remain. MIME claims must match validated signatures (generic octet-stream is allowed); path/drive/NUL/malformed original filenames are rejected, and multer preserves paths so validation can see them. Storage paths continue to use server-generated UUIDs only.

DOCX central-directory validation rejects duplicate/traversal/encrypted/macro entries and caps entries (10,000), both declared and actually streamed expanded bytes (100 MiB) and content-types XML (1 MiB). Mammoth has external-file access disabled. No remote URL upload or public object URL is added. Extraction rejects PDFs above 1,000 pages, text above five million characters, or DOCX HTML above ten million characters; the existing 10,000-chunk cap and OCR timeout remain. PDF/DOCX parsing is not a hardened process sandbox. Object buckets remain private; backend/worker storage credentials never enter public responses. Archive limits are not a malware sandbox; production should add resource containment and malware scanning if required by its threat model.

## Audit, logs and metrics

Audit events store safe identifiers, action, target type/ID, generated request ID, timestamp and a tiny metadata allowlist (result/count/enabled/role). No chat, document, password, cookie, token, prompt, vector or header content. Authentication events are global; owner/admin organization audit reads use `GET /api/organizations/:organizationId/audit-events?limit=50&offset=0` (maximum 100/page). Tenant events cannot be read across organizations. UPDATE/DELETE are rejected by the database trigger; no application edit API exists. Historical IDs are snapshots without cascading FKs. A privileged DB administrator can still change triggers/tables; production needs least-privilege credentials and immutable external retention where required.

Existing chatbot-create/upload/retry handlers await audit insertion before returning success. Those accepted service operations and audit insertion are separate commits; a database failure between them can leave the operation completed but its audit missing. Public security settings, organization ownership, auth session creation/revocation and bootstrap are transactionally audited. Stronger cross-service audit atomicity/outbox handling is a documented beta limitation.

Pino logs generated request IDs, method/status and fixed safe failure categories; URLs/query strings, request bodies and credential headers are omitted. Defensive redaction includes password/session/CSRF/storage/metrics secret fields. Existing RAG/ingestion logs contain counts, safe IDs and timings only.

`/internal/metrics` returns 404 unless metrics are enabled and the independent Bearer token matches. Do not place this token in a URL. Prometheus format exposes HTTP counts/status/durations and fixed counters for public chat/failure/fallback, rate-limit blocks and login failures. Labels use fixed route classes/status/event names, never tenant/user/document/public IDs, paths, filenames or content. Worker success/failure/duration remain in safe structured logs; this beta does not add a worker metrics listener or central metrics persistence. Use external scraping, alerting and log aggregation.

## Backup and recovery

Backups are ignored by Git and the Docker build, private on disk, and must be encrypted for offsite storage. They contain customer data and password/session hashes; apply restricted access, retention and tested key recovery.

```sh
cd backend
npm run backup:postgres  # local Compose PostgreSQL 17, custom pg_dump format
npm run backup:verify    # also restore ONLY to a random north_orbital_restore_check_* DB
npm run backup:objects  # requires local S3 endpoint/credentials in private environment
```

`backup:verify` checks a nonempty dump, migrations, security/vector tables, nonempty tenant rows and ready-document/chunk consistency, then drops only its randomly generated temporary database. It never restores over/drops the active database. This Compose convenience script targets the existing local database/user by name. For another deployment use its private connection configuration with `pg_dump -Fc --no-owner --no-acl` and `pg_restore --exit-on-error --no-owner --no-acl --dbname RESTORE_DATABASE backup.dump`. Create a separate PostgreSQL 17 database with pgvector/pgcrypto available, verify migrations/table counts and application readiness before a controlled cutover. Do not use `--clean` against the active database.

Object backup uses paginated S3 List/Get operations, conditional ETag reads, numbered local files and a private manifest with original object keys, sizes and SHA-256 checksums. It does not copy Docker volumes. Only counts/bytes are printed. A missing manifest denotes an incomplete backup. Restore validates all files/checksums before writing and requires a separate existing empty bucket:

```sh
cd backend
npm run restore:objects -- --directory ../backups/objects/BACKUP_DIRECTORY \
  --bucket north-orbital-restore-check
```

Keep the restore bucket private and explicitly switch application configuration only after verification. Existing objects are not overwritten (`If-None-Match: *`); the configured live bucket cannot be the restore destination. Bucket creation/encryption/lifecycle policy remain an operator responsibility.

For a consistent beta backup, put ingress in maintenance mode, stop accepting uploads/retries/mutations, let worker jobs finish, stop the worker gracefully, then capture database and objects while writes stay paused. Restart the worker and re-enable writes after both complete. Running independent live backups is not a distributed snapshot: objects/jobs can change between captures. Production should use coordinated snapshots or versioned objects plus WAL/PITR and backup reconciliation. Document an RPO/RTO and rehearse restore regularly; a successful dump alone is insufficient.

| TRUST_PROXY_HOPS | 0; integer 0–5 |
| METRICS_ENABLED / METRICS_TOKEN | false / independent strong token required when enabled |

Generate secrets with a CSPRNG; never reuse example text or storage credentials. All backend instances need matching rate-limit configuration/secret. Secret rotation resets limiter identity; schedule it deliberately. Session hashes do not depend on the rate secret. Do not print resolved Compose configuration because it contains credentials; use `docker compose config --quiet`.

```sh
cd backend && npm run security:init
cd ..
docker compose config --quiet
docker compose build
docker compose up -d backend worker
# no volume deletion or down -v
docker compose ps
curl -fsS http://localhost:3001/api/health
curl -fsS http://localhost:3001/api/ready
```

Backend and OCR worker run as `node`; OS/npm/OCR packages are installed at build time. The migrations stage is a separate administrative job. Production deployment must replace Compose's existing local-only database/storage credentials, use TLS, restrict infrastructure networking, provide least-privilege database/S3 users and secrets, and monitor backups/5xx/latency/worker failures.

## Verification commands

Use Node 22.23.2 or a compatible supported version. `DATABASE_URL` must point to the local test-capable PostgreSQL 17 instance. Integration tests use rolled-back fixtures or isolated random schemas, and coordinate node-pg-migrate advisory locks.

```sh
cd backend
npm run build
npm test
npm run test:db
npm run evaluate:rag
npm audit --omit=dev
cd ../widget
npm ci
npm run build
npm test
cd ../frontend
npm run build
npm test -- --watch=false
```

The existing RAG/handler tests now inject a test-only authenticated principal, without changing production's fail-closed behavior. The new security integration suite uses real Argon2 hashes, cookies, memberships, sessions, limits, public settings and PostgreSQL retrieval with deterministic model/embedding fixtures. It tests two users/organizations and multiple chatbots, role/IDOR rejection, CSRF, expiry/logout, disabled/public ID rotation, origin/CORS, safe config, ready-only cross-scope sources, audit immutability/privacy, deterministic rate reset/concurrency and cleanup.

Opt-in live smoke (uses the explicitly supplied accepted local tenant; enables public access, adds localhost origin, preserves existing origins, and creates/reuses an owner through the stdin CLI):

```sh
cd backend
node scripts/verify-public.mjs \
  --organization f94827a2-4ec3-4bd0-92cc-49accd1cdf9b \
  --chatbot f732a2ca-55b2-47fa-aefa-1fb497e56262
node scripts/verify-log-privacy.mjs
```

The smoke creates `.env.smoke.local` with mode 0600 for the local owner's credentials, never prints credentials/content, logs out afterward, and prints only checks and the nonsecret public ID. It asks the volunteer cancellation question, validates a supported answer/citations, checks the public source namespace/fake source, rejects missing/bad origins and unauthenticated administration, tests 429/Retry-After, widget content type, health and protected metrics. Its final rate test deliberately exhausts the public client's current window; allow the next minute before manual chat.

Existing `verify-ingestion.mjs` and `verify-rag.mjs` use a generated temporary authenticated principal, then clean up only their own temporary users/tenants/objects. The ingestion smoke covers PDF, DOCX, raster PDF/OCR, 1,024-dimensional vectors, terminal retries and manual retry. Audit records remain append-only after smoke fixture cleanup.
